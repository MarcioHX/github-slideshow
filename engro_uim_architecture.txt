1. PROJECT OVERVIEW
--------------------------------------------------------------------------------

Project Name     : UIM (Universal Intelligence Market)
Operator         : Engro
Geographic Scope : National — Republic of Mozambique
Purpose          : A national-scale market intelligence platform for collection,
                   validation, processing, and distribution of agricultural
                   market price data across provinces and districts.

Primary Users
  - Collectors       : Field agents who submit daily market price data
  - Subscribers      : Organizations and individuals who consume validated
                       market intelligence via the UIM-X platform
  - Administrators   : Internal team managing platform operations

Primary Operations
  - Collection of raw market submissions from field collectors
  - Automated validation, cleaning, and anomaly detection via Sentinel A1
  - Distribution of processed market intelligence to subscribers
  - Subscription and access management via UIM Core Backend
  - Predictive analytics and price forecasting (roadmap)

────────────────────────────────────────────────────────────────────────────────
COMPONENT : Sentinel A1
────────────────────────────────────────────────────────────────────────────────
Provider       : Render Services, Inc.
Type           : Background Worker (persistent, non-HTTP)
Layer          : LAYER 4 — Data Processing
Initial Tier   : Starter
Capacity       : 0.5 vCPU (shared), 512 MB RAM
Upgrade Trigger: When batch processing cycle duration approaches or exceeds
                 the threshold polling interval, or when backlog of unprocessed
                 rows accumulates across consecutive cycles.
Runtime        : Python
Execution Model: Threshold-based polling loop
                   - Worker runs continuously
                   - Checks pending raw row count
                   - If row count meets threshold: triggers processing pipeline
                   - Sleeps and repeats
Not Triggered By : HTTP requests, external API calls, or cron schedule
Role           : Asynchronous data-processing engine for UIM platform.
                 Responsibilities:
                   - Read raw unprocessed submissions from Main Database
                   - Convert raw rows into structured DataFrames
                   - Execute analytics pipeline (imported Python modules)
                   - Write approved, rejected, and incident records to database
                   - Log processing status, row counts, and timing per function
                   - Flag anomalies and outliers for review
Analytics Pipeline (imported from analytics modules):
  Phase 1 — Data Quality & Processing
    - Data cleaning
    - Preprocessing and standardisation
    - Smoothing
    - Outlier detection
    - Anomaly detection
    - Validation and approval/rejection classification
  Phase 2 — Forecasting (roadmap / future integration)
    - Price forecasting
    - Availability forecasting
    - Predictive trend estimation
Communicates With :
  - Main Database (read raw submissions, write processed results)
  - No public HTTP interface
  - No direct communication with UIM Core Backend
Not Exposed To : Public internet
Cost Category  : Infrastructure

5. ANALYTICS RESEARCH LAYER (SEPARATE REPOSITORY)
--------------------------------------------------------------------------------

This layer is NOT a deployed service. It is an offline research and module
authoring environment operated by the analytics team. Its outputs (.py modules)
are integrated into Sentinel A1 by the platform engineer.

Repository Name  : Sentinel Analytics Repo (separate from production repo)
Operated By      : 2 Python data analysts
Access Scope     : analytics/ and notebooks/ directories only
Integration Path : Analyst produces .py modules → engineer reviews PR →
                   engineer integrates modules into Sentinel A1 production repo

────────────────────────────────────────────────────────────────────────────────
SUB-COMPONENT : Data Quality & Processing Modules
────────────────────────────────────────────────────────────────────────────────
Location       : analytics/data_quality_processing/
Files          :
  - cleaning.py       : Raw data cleaning and null handling
  - preprocessing.py  : Standardisation, type casting, normalisation
  - smoothing.py      : Time-series and price smoothing logic
  - scaling.py        : Value scaling and normalisation functions
  - outliers.py       : Statistical outlier detection
  - anomalies.py      : Anomaly identification and flagging
  - validation.py     : Business rule validation and row classification
Design Rule    : All functions are pure Python, importable, stateless
                 where possible. No database connections, no file I/O,
                 no notebook-only logic. Input: pandas DataFrame.
                 Output: structured DataFrame or results dictionary.

────────────────────────────────────────────────────────────────────────────────
SUB-COMPONENT : Forecasting Modules
────────────────────────────────────────────────────────────────────────────────
Location       : analytics/forecasting/
Files          :
  - price_forecast.py         : Predictive price modelling
  - availability_forecast.py  : Availability and supply estimation
  - models.py                 : Shared model definitions and utilities
Status         : Roadmap — not in initial Sentinel A1 deployment
Design Rule    : Same as Data Quality & Processing modules above

────────────────────────────────────────────────────────────────────────────────
SUB-COMPONENT : Evaluation Notebooks
────────────────────────────────────────────────────────────────────────────────
Location       : notebooks/
Purpose        : Orchestration and evaluation harness only.
                 Notebooks do NOT contain production analytics logic.
                 All logic lives in .py modules. Notebooks only import,
                 execute, and evaluate.
Evaluation Outputs per notebook run:
  - Total input rows
  - Total approved rows
  - Total rejected rows
  - Acceptance and rejection rates
  - Outlier counts and distribution
  - Anomaly counts and flags
  - Missing critical field counts
  - Data distribution / coverage consistency
  - Execution time per function and per module
  - Total pipeline runtime
Dataset Used   : 3 months of historical market submission data (.csv)

────────────────────────────────────────────────────────────────────────────────
SUB-COMPONENT : Pipeline Sequence Document
────────────────────────────────────────────────────────────────────────────────
File           : docs/pipeline_sequence.md
Contents       :
  - Ordered sequence of modules and functions to apply
  - Required inputs and expected outputs per function
  - Assumptions and threshold values used
  - Functions identified as CPU-intensive
  - Functions identified as RAM-intensive
  - Optional vs mandatory pipeline stages
Purpose        : Handoff guide for platform engineer to integrate modules
                 into Sentinel A1 runtime without analyst involvement

6. DATA FLOW SUMMARY
--------------------------------------------------------------------------------

[Collector] 
    → HTTPS POST → [Cloudflare WAF/DDoS] 
    → [UIM Core Backend API] 
    → INSERT raw submission → [Main Database]

[Sentinel A1 — polling loop]
    → SELECT raw pending rows → [Main Database]
    → load into DataFrame
    → apply Data Quality & Processing modules
    → apply Forecasting modules (future)
    → WRITE approved / rejected / incidents → [Main Database]
    → log metrics and timing

[UIM X Frontend]
    → HTTPS GET → [Cloudflare WAF/DDoS]
    → [UIM Core Backend API]
    → SELECT processed data → [Main Database]
    → return structured response → render dashboard

[Analytics Team]
    → SELECT read-only → [Main Database] (DBeaver, restricted user)
    → prototype and validate in notebooks
    → produce .py modules
    → submit PR to analytics repo
    → engineer reviews and integrates into Sentinel A1

11. SCALING NOTES FOR ARCHITECTURAL DRAWINGS
--------------------------------------------------------------------------------

- All application compute starts on Starter tier (0.5 vCPU / 512 MB RAM)
- Standard tier upgrade (1 vCPU / 2 GB RAM) is triggered by observed
  latency, backlog growth, or memory pressure — not by a fixed user count
- Sentinel A1 upgrade is triggered by batch processing time exceeding
  the polling interval, not by row count alone
- Database storage scales independently of compute tier
- Both frontends are static sites and scale via CDN — no compute tier applies
- Cloudflare security layers are cloud-scale and have no fixed capacity ceiling
- National-scale ambition requires a clear upgrade path from Starter to
  Standard and beyond on API and worker components as collector and
  subscriber numbers grow
